It remains unchanged. `loader.js` loads that module; frozen runtime URLs contain

`wasm-validate --enable-threads` passes. Memory64 and SIMD are enabled by
default in 1.0.42. `wasm-objdump -h/-x`, `wasm-stats --enable-threads` and
`wasm2wat --enable-threads` examined the actual module. Full WAT was 591,424,118
bytes; the retained gzip is 51,952,785 bytes. These are analysis outputs, not
deployment assets. Structural findings:

- 1,969 types, 86 imports (85 functions and one memory), 91,026 defined
  functions, 22 exports, 4,077 data segments and 18,984,700 static opcodes.
- Imported `env.memory` is shared **i64** memory: 49,152 initial pages (3 GiB)
  and 262,144 maximum pages (16 GiB). These are capacities, not resident RAM.
- Initial mutable `__stack_pointer` is 33,798,800. Stack base/end globals also
  exist; no original compiler/link flags or complete thread-stack budget is
  recoverable from these observations.
- Code: 48,192,941 bytes; data: 7,828,019; retained name section: 6,823,623.
  Symbols are useful for diagnosis but do not supply original C++ or DWARF.
- SIMD, atomic threading, `memory.copy` (6,704 static occurrences),
  `memory.fill` (9,562) and bulk initialization are present. Counts are **not**
  runtime costs. Disabling SIMD rejects the module's types.
- Host imports include time/audio/input, HTTP filesystem, user saves,
  Emscripten pthreads and `wgpu_start_worker`. There is no exported complete
  alternative WebGL renderer or scene-level JavaScript gameplay API.

For bounded pseudocode work, original WAT bodies of `wasm_httpfs_active` and
`emscripten_stack_get_current` were extracted into an analysis-only module.
The original call-once dependency was declared as an external import with its
i64 signature, rather than replaced with pretend recovered engine code.
1.0.41 `wasm-decompile --enable-memory64 --enable-threads` generated 420 bytes
of pseudocode: HTTP FS activation tests an atomic initialization state, calls
the once initializer, then reads a flag; stack-current returns the i64 stack
pointer. This does not identify either function as a runtime hotspot. The
full 91,026-function engine was not decompiled unnecessarily. `wasm2c` was not
used: translating all dependencies would not reconstruct an original build.

The new small startup probe was generated by WABT. It actually executes an
i64/BigInt function against shared memory64, SIMD, bulk-memory and atomic-load
instructions in a 64 KiB module before starting workers or downloading game
data. It does not allocate the native 3 GiB heap and therefore does not prove
that a device can allocate or sustain that heap.

## iPhone 11 Pro compatibility boundaries

User reports iOS **26.x**, without an exact minor version or measured session.
No physical iPhone is attached to this environment. Real-device FPS, memory,
background/resume behavior and sustained thermal stability remain unverified.

Safari 26 has WebGPU, but API presence alone is insufficient. Apple's
[Metal feature tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf)
classify A13 as Apple GPU family 6 and introduce BC pixel formats with family 9,
with some exceptions for family 7/8 iPads. The current renderer requires BC
compression and the actual game uses BC1/2/3/4/5/7. The iPhone 11 Pro's A13
therefore does not provide the native texture path this renderer expects.
Browser feature reporting is still checked at runtime.

Reducing resolution cannot solve incompatible memory64 or texture formats.
A viable iPhone renderer needs verified BC decoding/transcoding (including BC6/7,
mips, arrays and cubes), bounded upload accounting and compatible shader/device
limits. Decoding everything to RGBA increases texture memory and is unsuitable
as an unmeasured blanket workaround. A smaller native heap/memory32 build needs
the actual native source/toolchain; changing only the glue's heap number would
violate the module's declared minimum. Original assets must remain intact.

A WebGL2 replacement must also implement the native ring's complete graphics,
compute, readback and resource-lifetime contract; renaming WebGPU calls would
not achieve compatibility. The existing CPU shader subset remains incomplete
for game rendering. See `CPU_RENDERER_STATUS.md` for measured scope.

The host now chooses conservative defaults on touch-only devices even when
Safari omits `deviceMemory`: low quality, two engine cores, 640×360 internal
targets and the native 30 FPS limit. Explicit test settings override these
defaults. Fixed native targets preserve the existing fullscreen crash fix;
adaptive native resizing is deliberately not enabled without a safe engine
resize path. Touch controls write the existing shared input ABI for movement,
camera, interaction, entering a car, jump/brake, radio wheel and pause. They
release held input on cancellation/backgrounding. These are regression-tested
host behaviors, **not verified iPhone gameplay**.

## Reproduce and release gates

Run `python performance/run_checks.py` (Node and Python required), then use
the actual staged browser build with `profile=1`. `nocache=1` exercises memory
cache fallback; `low=1&res=640x360&fps=30` selects a repeatable low profile.
Default desktop native targets and graphics are preserved. The profiling
report explicitly separates active renderer CPU time from async GPU pass
timestamps and does not pretend to separate native physics/NPC costs.

Original module verification with official WABT:

```text
wasm-objdump -h game.wasm
wasm-objdump -x game.wasm
wasm-stats --enable-threads game.wasm
wasm-validate --enable-threads game.wasm
wasm2wat --enable-threads game.wasm -o analysis-only.wat
```

Do not publish analysis outputs, tooling, credentials or original world archives.
Existing immutable packs, manifests, shader URLs and private R2 data are retained.
Use the versioned static-asset release and explicit frozen stage described in
`CLOUDFLARE_DEPLOYMENT.md`; deployment is not proof of mobile support.
